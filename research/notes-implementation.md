# Implementation notes — Cortex-managed executable Entities

Deviations from the design text, probe-driven decisions, and the reasoning
behind them. Design: `cortex-managed-entities-design.md`; probe findings:
`notes-preflight.md`, `probe-property-task-findings.md`.

## 1. Fresh module generations (never redefine in place)

Re-declaring a same-named Workflow task in a live module is unreliable:
`Persist.memory` memoizes `Task` objects, so the *first* body keeps running
(probe: a redefined body returned the first result at the same path).
Therefore each manifest (active definitions of a type, topologically sorted)
compiles into a **new anonymous module** keyed by the manifest digest in
`Cortex.managed_entity_registry`. Consequences:

- a definition update builds a new generation and re-points the registry;
- dropping a property means the new module simply lacks it (the old module
  keeps it; nothing is removed from live modules);
- ownership tracking is a process-level set of installed
  `(type, property)` pairs.

The module's `name` is assigned the entity type string (`mod.name = 'Gene'`)
and `entity_name` its underscored form, *before* any task declaration — the
entity input declaration needs them, and they give clean job paths
`var/jobs/Gene/<property>/<entity>`.

## 2. Identity inputs have no defaults

`_cortex_definition`, `_cortex_definition_version`, `_cortex_definition_digest`
are declared on every property task and are passed explicitly on every call.
The design text suggested defaults from the active meta; that is wrong:
defaults equal to the active value never reach `non_default_inputs`, so the
job hash would not change when a definition is updated — evidence would be
served stale. No defaults, always-forward is the correct rule.

## 3. `dep` blocks forward options *and* the dependency's own identity

The design's dep block was:

```ruby
mod.dep(:raw_activity) do |jobname, options|
  mod.job(:raw_activity, options[mod.entity_name] || options[:gene], options)
end
```

Forwarding the parent's options alone propagates the **parent's** identity
inputs, so updating the dependency changed only the parent's path. The
implemented block also (a) slices the dependency's *declared* arguments and
(b) overwrites the identity inputs with the **dependency's** own
(`identities[dep]`). Result: updating `raw_v` moves both `raw_v`'s and
`derived`'s job paths, and `derived` recomputes (asserted in the suite and
shown in the e2e transcript).

## 4. Upstream `property_task` forwarding defect → our wrapper

The public property method generated by `property_task` does not forward
`*args` to `<property>_job` (scout-gear 10.12.2). We install our own
wrapper with `define_method(<prop>)` after `property_task`:

- `:single` / `:both`: `<prop>_job(*args, **kwargs)` then run/load;
- `:array` with a scalar receiver: `make_array` + member selection
  (`res[container_index]` when contained, else `res[self] || res[0]`).

## 5. Bodies compiled from the definition file

The author's body is read with `File.read` and wrapped in a `Proc` evaluated
with the `.rb` file as filename (and line 1), so syntax errors and
backtraces cite the definition file rather than the engine. Candidates
staged by `define`/`update`/`validate` compile in a **scratch module** with
the same envelope (fresh anonymous module + identity inputs + wrappers), so
errors surface before anything is written.

## 6. Closure-aware required arguments

`activity_call` legitimately takes `treatment` that only its dependency
`raw_activity` consumes. The naive "unknown argument" check would reject it,
and forwarding it blindly would leave the dependency's task missing a
required input. Implemented rule: an argument must be declared by the
property or by some property in its dependency closure; a missing required
argument of the closure raises naming the property that needs it. This
yields a real `Gene/raw_activity/…` Step dependency (suite asserts
`job.dependencies` contains it).

## 7. Pre-write graph validation + write order

Before anything is written, `define`/`update`/`validate` check the
**would-be** graph: dependencies must be active same-type properties and the
graph must stay acyclic. Writes are body-first, metadata last — a crash in
between leaves an orphaned body that cannot be activated (nothing resolves
without `.meta`), which is the safe direction for executable code.

## 8. Cross-map ambiguity is a hard error

Unlike content namespaces (first map wins, ambiguity merely reported), an
executable definition found in two distinct physical locations raises in
`property_definition`, `load_entity_type`, and the manifest builder. Two
copies of code at one address must never be silently merged.

## 9. Foreign `Entity` modules are not adopted

The design allowed reusing an existing Entity module after a compatibility
check. Probes showed the check is not sound: a module whose tasks were
declared once cannot be recompiled (same memoization problem as §1), so
adoption would silently pin stale bodies. The engine therefore **rejects**
foreign `Entity` modules with an actionable message (rename the type or
remove the constant), while a plain non-Entity constant is likewise
rejected. Name collisions with non-Cortex properties raise (ownership set).

## 10. `entity_property` demonstrator removed

The old task's `entity_type` input carried entity *options* (not a type
name), so no clean alias to `cortex_entity_property` exists. It was deleted
rather than kept as a broken alias; README documents the replacement.

## 11. Task receipts

`cortex_entity_property` returns exactly the 8 keys
`{entity_type, entity, property, arguments, definition_version,
definition_digest, property_job, result}` with `property_job` as a Step
`short_path` (String, or Array for list receivers). No `agent_meta` is
attached: the producing step is the provenance. Note for replay: the
workflow task itself is content-addressed on its inputs, so an identical
call replays the receipt from cache (see `tmp/e2e_entities.rb`, which cleans
the workflow job to re-execute while the property job stays cached).

## 12. Two pre-existing test failures fixed in the tests

Proven to fail on pristine HEAD~1 before this milestone:

1. *resource_paths dedupes maps* — assumed `read_maps` was
   `[:lib, :current]`; `:user` resolves to a distinct directory, so two
   candidates is correct. The check now asserts the dedupe property
   directly (`[:lib, :current]` → 1; `[:lib, :current, :user]` → 2).
2. *legacy `:current` data* — depended on a live conversation (`Summing`)
   that had been cleaned up; the check now writes its own fixture.

## 13. Sandbox / test harness details

- `Scout::Config.set` in-process is unreliable for `read_maps` (token
  priority semantics), so tests set `Scout::Config::CACHE['cortex']`
  directly with token-level entries.
- The engine freezes the var root at require time (task bodies run with a
  different CWD than repo-root calls); scratch roots must therefore be
  configured **before** requiring `lib/Cortex/entities`.
- `bash` runs under bwrap and fails on `/bulk` paths: prefix with
  `BWRAP=false`.
- Suites clean `var/cortex/entities` and `~/.scout/var/jobs/<Type>` around
  runs.

## 14. Deliberate non-goals this milestone

- `cortex_list` / `cortex_read` / `cortex_write` / `cortex_search`
  select_options unchanged (input descriptions are stable prompt state);
  `cortex_search` does not index definitions — discovery is
  `cortex_property_list`.
- No cross-entity-type dependencies.
- No sandboxing of property bodies: definitions are trusted executable Ruby,
  written by agents that already have workspace write access.

## Refinement round: array/both receivers, task-layer guards

15. **`array` on a scalar receiver returns the member value, not a Step crash.**
    Upstream `Entity::Property` implements the array property by calling the
    underlying job and selecting `res[container_index]`/`res[self]`, which
    explodes when the receiver is a plain annotated String rather than a
    contained member (`NoMethodError: undefined method '[]' for Step`).  The
    engine's `run_entity_property` now drives `<prop>_job` directly and, for
    `array`/`both` properties, treats the returned Step as the container and
    loads the value the property semantics call for (member selection for a
    contained scalar, the container value for a list receiver).  Verified by
    `tmp/verify_array_fix.rb` (array/both × scalar/list, engine and task layer).

16. **`both` bodies see `entity_list` on list receivers.**  The list input
    arrives as an input (`list`), but author bodies are written in the natural
    Entity idiom (`entity_list`).  The compile envelope now declares the
    `entity_list` helper on the property's step methods for `array`/`both`
    properties, so `Array === entity_list` branches work as designed.
    (`:single` bodies never see it.)

17. **Task layer guards inactive properties.**  `cortex_entity_property` now
    re-checks `active` after loading the definition and raises a clean
    `ScoutException` instead of letting the engine's module lookup fail.

18. **`:json` step results are symbol-keyed when `exec`'d.**  Verification
    scripts must read receipts with symbol keys (`r[:result]`); the persisted
    JSON round-trips to strings.  No engine change; documented for probes.

19. **`property_job` shape follows the receiver, not the property type.**
    `array` on a list receiver returns an Array of Steps (one per member);
    `both` on a list receiver is a single container job (String path).
