Coverage summary (each area is one or more test methods):

- **names** — valid/invalid entity type (constant segments incl. `::`),
  snake_case property, reserved names (`job`, `entity`, `entity_list`,
  `inputs`, `step`, `dependencies`, `*_job`, `_cortex_*`; arg reserved:
  `entity`, `list`, `jobname`, `_cortex_*`)
- **lifecycle** — define v1 (body+meta on disk); duplicate define raises;
  update with stale `expected_version` raises (message lists both
  versions); correct update → v2 + `.history` snapshot (`NNNNNN.rb` +
  `NNNNNN.json`); a syntactically broken candidate leaves active v1 intact;
  remove with wrong version raises; correct remove → `.rb` deleted, meta
  tombstone (`active:false`, `removed:true`), history preserved; redefine
  after remove starts a fresh version 1
- **dispatch** — `single` on scalar and on list (maps per member); `array`
  on list and on scalar (member selection; see the refinement note below);
  `both` on scalar (`entity`) and on list (`entity_list` branch); argument
  forwarding (kwargs reach the body via `inputs`)
  - refinement: the original engine-level `array`-on-scalar and
    `both`-on-list paths crashed (`NoMethodError`, `NameError`); they were
    fixed and are now asserted by `tmp/verify_array_fix.rb` (8/8) and
    covered in the receiver-shape table in `doc/developer/Entities.md`;
    the suite's `array` dispatch check still uses the task layer
- **deps/cache** — `A` depends on `B`: real `Step` dependency
  (`job.dependencies` includes B's path); updating B (new digest) moves
  **both** B's and A's job path; identical repeat execution loads from cache
  (counter-file instrumentation: no recompute); `update: true` cleans and
  recomputes at the same path
- **graph** — missing dependency raises; cycle raises
- **namespace safety** — unrelated constant (plain module) is rejected;
  foreign `Entity` module cannot be adopted (raises, actionable message);
  name collision with a non-Cortex property raises; two entity types may
  share a property name
- **receipts** — exactly the 8 keys; `property_job` is a `String` (or
  `Array` for a list) matching the module/task/entity path; result equals
  the body output; `definition_version`/`definition_digest` match the meta
- **pagination** — `cortex_property_read` body pagination reports the next
  window; the suite covers the partial last page and reading at/past the end
  of a one-line body (`body lines 1-1 of 1`); the multi-page `# next: N`
  branch (`lib/Cortex/tasks/entity.rb`) is NOT exercised by any current
  artifact — covered cases are only the last-partial-page and `(end)`
  cases
- **path safety** — entity type `..`, `Foo/../Bar` rejected; property
  `../x` rejected
- **cross-map ambiguity** — the same `<Type>/<prop>.rb` written into two
  distinct scratch maps makes `property_definition` and `load_entity_type`
  raise

## test/test_cortex_workspace.rb

`BWRAP=false ruby test/test_cortex_workspace.rb`

```
SUITE: 29 passed, 0 failed, 0 errored
```

Two pre-existing failures were fixed by fixing the *tests* (both were proven
to fail on pristine HEAD~1 `workflow.rb` before this milestone):

1. *resource_paths dedupes maps that resolve to the same dir* — asserted one
   candidate for a name present in `:lib` and `:current`, but `read_maps`
   also includes `:user`, which resolves to a genuinely distinct physical
   directory, so two candidates is correct behavior. The check now asserts
   the dedupe property directly: `[:lib, :current]` (same dir here) yields
   one entry, `[:lib, :current, :user]` yields two distinct dirs.
2. *legacy `:current` data is listable/readable/searchable* — depended on a
   conversation named `Summing` existing in the live workspace; it had been
   cleaned up during earlier testing. The check now writes its own minimal
   fixture first, then lists/reads/searches it.

own `Gene` definitions and job dirs first and again unless `KEEP=1`); the

1. `cortex_property_define Gene/test` (single, one required argument) →
   `{address: "Gene/test", version: 1, digest: …, defined: true}`
2. `cortex_entity_property` for `Tp53` → receipt with exactly 8 keys,
   `result` from the body, `property_job` `Gene/test/Tp53_…`
3. replay → identical `property_job` and result (cache hit, no new step)
4. `update: true` → recomputed at the **same** path

   `raw_v`) → `derived` result incorporates `step(:raw_v).load`
6. updating `raw_v` → **both** the dependency's and the dependent's job
   paths change, and `derived` returns the new value

removed before and after the run.
